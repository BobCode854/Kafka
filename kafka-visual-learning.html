📂
Partition
An ordered, immutable sequence of records. Each partition is an independent log. A topic with 3 partitions can be consumed by up to 3 consumers in parallel. Partitions are what give Kafka its horizontal scale.
topic=orders, partition=1 → independent log file per broker
📄
Segment File
Each partition is split into multiple segment files on disk (e.g. 1 GB each). Kafka never edits a segment — it only appends. When a segment reaches log.segment.bytes, it's closed and a new one starts. Old segments are deleted by retention policy.
00000000000000001000.log → offsets 1000 to 1999
🔢
Offset
A monotonically increasing integer assigned to each message within a partition. Offsets start at 0 and never repeat or decrease. Consumers track their position using offsets. Offsets are per-partition — Partition 0 and Partition 1 each have their own offset-0.
P0:offset=5 and P1:offset=5 are two different messages
📏
LEO — Log End Offset
The offset of the next message to be written by the leader. It represents the very latest position on the leader's log. Followers try to catch up to the leader's LEO by fetching messages continuously.
Leader wrote offset 47 → LEO = 47
💧
HWM — High Watermark
The offset up to which all ISR replicas are synced. Consumers can ONLY read messages below the HWM — not the gap between HWM and LEO. This prevents reading data that might be lost if the leader crashes before replication.
LEO=47, HWM=46 → consumer can only read up to 46
🛡️
ISR — In-Sync Replicas
The set of replicas that are fully caught up with the leader's log. A replica falls out of ISR if it hasn't fetched from the leader within replica.lag.time.max.ms (default 30s). The leader tracks the ISR list and only advances HWM when all ISR members confirm.
ISR = [broker-0, broker-1, broker-2] → all in sync
🗂️
Index Files (.index, .timeindex)
Each segment has two companion index files. .index maps offsets → byte position for O(log n) lookup. .timeindex maps timestamps → offsets for time-based seek. Without these, finding offset 47,000 would require scanning the entire log file.
00000000000000001000.index + .timeindex
⏱️
Retention Policy
Kafka keeps data for a configured duration (retention.ms) or size (retention.bytes). When a segment (not a message) exceeds the retention boundary, the entire segment is deleted. Log compaction is an alternative — keeps only the last value per key forever.
retention.ms=604800000 → delete segments older than 7 days
SIMPLE EXPLANATION

All 8 Concepts — In Plain Words, Point by Point

📂 1. Partition THE BASIC UNIT
  • A topic is split into partitions. Think of a topic as a highway and partitions as the individual lanes on that highway.
  • Each partition is an independent, ordered list of messages stored on disk — like a numbered queue that never changes order.
  • Messages inside a partition are always in the same order — message 5 always comes after message 4. This order never changes.
  • A topic with 3 partitions can be read by 3 consumers at the same time — one consumer per partition. This is how Kafka scales.
  • Each partition lives on one broker as the leader, with copies (replicas) on other brokers for safety.
Real example: topic "orders" has 3 partitions → Consumer A reads P0, Consumer B reads P1, Consumer C reads P2 — all simultaneously
📄 2. Segment File HOW KAFKA STORES ON DISK
  • Kafka doesn't store a whole partition as one giant file. It breaks each partition into smaller files called segments — like chapters of a book instead of one huge book.
  • Each segment has a maximum size (default 1 GB, controlled by log.segment.bytes). When a segment fills up, Kafka closes it and opens a new one.
  • Kafka never edits or modifies a segment — it only ever appends new messages to the end. This is called an append-only log.
  • The segment filename tells you the first offset inside it. File 00000000000000001000.log starts at offset 1000.
  • Old segments are automatically deleted based on the retention policy (by time or by size). Kafka deletes whole segments at once — not individual messages.
  • There is always exactly one "active" segment per partition — the one currently being written to. All others are closed and read-only.
Real example: Partition 0 has 3 segments → ..0000.log (closed), ..1000.log (closed), ..2000.log (active, being written now)
🔢 3. Offset THE MESSAGE ID
  • An offset is simply a sequence number given to each message within a partition — like page numbers in a book. First message = offset 0, second = offset 1, and so on forever.
  • Offsets never go backwards and never repeat. Once offset 47 is used, it's used forever — even if you delete the message later (via retention), offset 47 will never be reused.
  • Offsets are per-partition, not per-topic. Partition 0 has its own offset 0, 1, 2... and Partition 1 has its own separate offset 0, 1, 2... They are completely independent counters.
  • Consumers use offsets as their bookmark — "I last read up to offset 47, so next time give me offset 48 onwards." This is how consumers resume after a crash.
  • You can seek to any offset at any time — go back to offset 0 and replay all messages, or jump to a specific timestamp. Kafka keeps all messages until retention expires.
Real example: P0:offset=5 and P1:offset=5 are TWO completely different messages — same number, different partitions
📏 4. LEO — Log End Offset LEADER'S LATEST WRITE
  • LEO stands for Log End Offset. It is the offset of the most recent message written by the leader broker to its local disk.
  • Think of it as the tip of the leader's pen — whatever the leader just wrote, that's where LEO points.
  • LEO moves forward the moment the leader writes a new message — before any followers have copied it. So LEO is always the most up-to-date position on the leader.
  • Each follower also has its own LEO — it represents how far that follower has replicated from the leader. Follower LEO < Leader LEO means the follower is still catching up.
  • Consumers cannot read up to the LEO — they can only read up to the HWM (see below). The gap between LEO and HWM is the "unsafe zone" — data written but not yet fully replicated.
Real example: Leader wrote offset 47 → LEO = 47. Followers are at offset 46 → their LEO = 46. Consumer can only read up to 46 (HWM).
💧 5. HWM — High Watermark SAFE-TO-READ BOUNDARY
  • HWM stands for High Watermark. It is the offset up to which ALL in-sync replicas (ISR) have confirmed they have the data.
  • Think of it like a flood watermark on a wall — the HWM marks the highest "safe" level. Everything below the HWM is replicated and safe. Everything between HWM and LEO is written but not yet replicated.
  • Consumers can ONLY read messages up to the HWM, never past it. This is Kafka's way of preventing consumers from reading data that might disappear if the leader crashes before replication.
  • The HWM advances only after all ISR replicas confirm they have fetched a given offset. With acks=all, the producer ACK is also sent only after HWM advances.
  • In a healthy cluster at steady state, LEO and HWM are equal or very close. A big gap between them means followers are lagging and that partition's durability is at risk.
Real example: LEO=47, HWM=46 → Consumer can only read up to offset 46. Offset 47 is written but not yet replicated, so it's invisible to consumers.
🛡️ 6. ISR — In-Sync Replicas THE TRUST LIST
  • ISR is the "trusted list" of brokers that are fully caught up with the leader. Only brokers in the ISR are considered reliable enough to become the next leader if the current leader fails.
  • Think of it like a team meeting attendance list. Only team members present and up to date can be trusted to lead the meeting if the current leader steps out.
  • A follower broker falls out of the ISR if it hasn't fetched new data from the leader within replica.lag.time.max.ms (default 30 seconds). Reasons: network issue, broker restarting, GC pause.
  • When a follower catches back up, it rejoins the ISR automatically — no manual intervention needed.
  • min.insync.replicas=2 means: "refuse the producer write if fewer than 2 ISR members exist" — this prevents accepting data that only 1 broker has, which would be unsafe.
  • The leader only advances the HWM after all current ISR members confirm they have fetched the latest offset. Non-ISR followers don't block this.
Real example: RF=3, all 3 brokers healthy → ISR=[broker-0, broker-1, broker-2]. broker-2 goes offline → ISR=[broker-0, broker-1]. HWM still advances, but with one fewer safety net.
🗂️ 7. Index Files (.index, .timeindex) THE FAST LOOKUP TABLE
  • Every segment file has two companion index files sitting alongside it. Without them, finding a specific message would be extremely slow.
  • .index file — Maps offset numbers to their byte position in the .log file. Imagine searching for page 47,000 in a 500,000-page book — without an index you'd flip every page. The .index file is the table of contents: "offset 47,000 is at byte position 2,938,742."
  • .timeindex file — Maps timestamps to offsets. Useful when a consumer wants to start reading "from 2 hours ago" — Kafka uses the .timeindex to find which offset corresponds to that timestamp.
  • Index files make offset lookups O(log n) — binary search — instead of O(n) linear scan. For a partition with millions of messages, this is the difference between milliseconds and minutes.
  • Index files are automatically rebuilt if deleted or corrupted — Kafka scans the .log file and regenerates the index on startup.
Files on disk: 00000000000000001000.log  +  00000000000000001000.index  +  00000000000000001000.timeindex
⏱️ 8. Retention Policy WHEN DATA GETS DELETED
  • Kafka keeps every message you send — unlike a traditional message queue which deletes a message after it's consumed. Retention policy controls how long Kafka keeps messages before deleting them.
  • There are two types of retention:
      • Time-based (retention.ms) — delete messages older than X milliseconds. Default: 7 days (604,800,000 ms).
      • Size-based (retention.bytes) — delete oldest messages when the partition exceeds X bytes. Default: -1 (unlimited).
  • Important: Kafka deletes entire segment files, not individual messages. If a segment contains messages from day 1 to day 7 and your retention is 6 days — the whole segment stays until all messages inside it are older than 6 days. You can't delete message #3 while keeping message #4 from the same segment.
  • Log Compaction is an alternative retention strategy (not deletion). Instead of deleting by time, Kafka keeps only the latest value for each key. Example: if you update user-123's address 10 times, compaction keeps only the most recent update. Used for changelog / event sourcing patterns.
  • Consumers are not affected by retention as long as they keep up. If a consumer is slower than the retention window (e.g. stopped for 10 days with 7-day retention), those old messages are deleted and the consumer will get a OffsetOutOfRangeException.
retention.ms=86400000 → keep 1 day
retention.ms=604800000 → keep 7 days
retention.ms=-1 → keep forever
Log compaction config:
cleanup.policy=compact → keep latest value per key
cleanup.policy=delete → time/size based (default)

👥 Many Producers → One Topic
Any number of producers can write to the same topic simultaneously. Kafka merges all their writes into the partitions based on the key. There's no coordination needed between producers.
🔀 Topic → Many Partitions
A topic is split into N partitions spread across brokers. Each partition is an independent, ordered log. This is what allows parallel reads and writes — different consumers handle different partitions at the same time.
📌 One Partition → One Consumer (per group)
Within a consumer group, each partition is assigned to exactly one consumer at a time. This guarantees in-order processing per partition. Two consumers in the same group will NEVER read the same partition simultaneously.
👁️ One Topic → Many Consumer Groups
Multiple different consumer groups can read the same topic independently. Each group maintains its own offset. Group A at offset 100 and Group B at offset 50 are completely independent — Kafka doesn't delete data just because one group consumed it.
⚖️ Max Parallelism = Partition Count
If a topic has 3 partitions, the max useful consumers in one group is 3. Adding a 4th consumer gives you an idle consumer — it gets no partition. More partitions = more parallelism potential, but also more broker overhead.
🔄 Producer ≠ Consumer Speed Coupling
Producers and consumers are completely decoupled in speed. The topic acts as a buffer. A producer can write 10,000 msg/sec and the consumer can process at 100 msg/sec — the topic absorbs the difference (up to retention limits).

What Happens When Things Go Wrong?

Three critical scenarios every Kafka developer must understand — network failures, broker failures, and speed mismatches.

SCENARIO 1
Producer Sends → Network Failure → Message Never Reaches Broker
What actually happens? Does the message get lost?

What Kafka Does Automatically
STEP 1
Producer's Sender thread gets a timeout or IOException. The send future resolves as a failure.
STEP 2
If retries > 0 (default: Integer.MAX_VALUE in modern Kafka), the producer waits retry.backoff.ms and retries the same batch.
STEP 3
The batch stays in the RecordAccumulator buffer during retries. It is NOT lost yet — it's queued in memory.
STEP 4
If network recovers before delivery.timeout.ms expires → message is delivered successfully. If not → producer throws exception to your callback.
⚠️ Risk: Duplicate on Retry
If the message DID reach the broker but the ACK was lost on the way back, the producer doesn't know. It retries → broker gets the same message twice. This is the at-least-once window.
Fix: enable.idempotence=true → broker deduplicates using ProducerID + sequence number
✅ What Protects You
enable.idempotence=true (default in Kafka 3+) assigns each producer a unique ID and a sequence number per message. The broker rejects exact duplicates — you get exactly-once producer semantics automatically.

What Happens — The Good News
KEY FACT
The message is NOT lost. It is durably stored in the broker's log. Network failure between broker and consumer only affects the consumer's ability to read — not the data itself.
STEP 1
Consumer's poll() call blocks waiting for the broker response. After request.timeout.ms, it throws a TimeoutException.
STEP 2
Consumer's heartbeat to GroupCoordinator also fails. After session.timeout.ms, the GroupCoordinator declares the consumer dead and triggers a rebalance.
STEP 3
Partition 1 (previously owned by Consumer 2) is reassigned to another consumer in the group. That consumer starts reading from the last committed offset — no data lost.
STEP 4
When Consumer 2's network recovers, it rejoins the group and gets partition(s) assigned again after the next rebalance.
⚠️ Risk: Duplicate Processing
If Consumer 2 had processed offset 47 but hadn't committed yet when the network died — the new consumer that takes over will re-read and re-process offset 47. At-least-once semantics in action.
✅ Why Data Is Safe
Data in Kafka is retained on disk independently of consumers. It doesn't disappear when a consumer disconnects. As long as a message is within the retention window, any consumer can read it at any time.
✅ Kafka's Pull Model Saves You
Because consumers pull data (not pushed), a disconnected consumer simply resumes from where it left off. The broker doesn't lose track of what it needs to send — it's all indexed by offset.

What Kafka Does (and Doesn't Do)
✅
Kafka does NOT slow down the producer. The producer writes at full speed. Partitions simply accumulate more messages. The topic is a buffer — that's its whole point.
✅
Kafka does NOT push messages to consumers. The slow consumer pulls at its own pace. It simply has an ever-growing lag but it won't crash.
⚠️
Lag grows = consumer falls behind. Eventually, if messages are being produced faster than consumed AND retention expires, old messages get deleted before the consumer reads them → data loss for that consumer.
⚠️
High lag = stale data. Consumer is processing messages from hours ago, not real-time. For time-sensitive processing (fraud detection, real-time dashboards) this is a problem.
How to Fix It — 4 Solutions
1. Scale Out Consumers
Add more consumer instances to the group. Kafka automatically rebalances — each new consumer handles some partitions. Max effective consumers = number of partitions.
2. Increase Partition Count
More partitions = more consumers in parallel. If you have 3 partitions and 10 consumers, 7 consumers sit idle. Increase partitions to 10 → all consumers work simultaneously.
3. Optimize Consumer Processing
Increase max.poll.records, use async processing, batch DB writes, use connection pooling. Make each poll() cycle process more records faster.
4. Set Lag Alerts (Monitoring)
Monitor kafka.consumer.fetch-manager-metrics → records-lag-max. Alert when lag exceeds a threshold. Use Kafka's kafka-consumer-groups.sh --describe to inspect lag per partition.

SIMPLE EXPLANATION

All 3 Failure Scenarios — In Plain Words, Point by Point

🔴 Scenario 1 — Producer Sends, But Network Cuts Before Reaching Broker PRODUCER SIDE FAILURE
Analogy: You send a letter, but it gets lost in the post. The recipient never received it — but you don't know that yet.
  • Your message is queued in memory first — Kafka never tries to send one message at a time. It batches them in something called the RecordAccumulator (like a tray of outgoing mail). When the batch is full or time is up, it sends.
  • Network fails → the send gets a timeout error — The producer's sender thread tried to deliver the batch to the broker, but got no response. It doesn't know if the broker got it or not.
  • Kafka automatically retries — The batch stays in memory and Kafka tries again after a short wait (default: 100ms). It retries many times (default: virtually unlimited) until a total time limit (delivery.timeout.ms = 2 minutes) runs out.
  • If network recovers in time → message delivered safely — Nobody noticed anything went wrong from the outside.
  • If network stays down beyond 2 minutes → your callback gets an error — At this point Kafka gives up and throws a TimeoutException. Your application code must decide what to do (retry itself, dead-letter queue, alert, etc.).
  • Dangerous hidden trap — duplicate messages — Imagine the message DID reach the broker, but the broker's ACK (confirmation reply) got lost on the way back. The producer thinks it failed → retries → broker gets the same message twice. Without protection, your consumer sees duplicate orders, payments, etc.
  • Fix: turn on idempotence — With enable.idempotence=true (default in Kafka 3+), every message gets a unique sequence number. The broker checks "have I already stored this sequence?" and silently discards the duplicate. You get exactly-once writes for free.
Without idempotence: retry → broker stores same message twice → consumer sees duplicate
With idempotence: retry → broker checks sequence number → silently ignores duplicate ✓
🟡 Scenario 2 — Message Is Safely in Kafka, But Consumer Can't Fetch It CONSUMER SIDE FAILURE
Analogy: The letter arrived safely at the post office, but the person who was supposed to pick it up got stuck in traffic. The letter waits safely; someone else can go pick it up.
  • The message is NOT lost — Once a message is written to the broker and replicated (past the High Watermark), it lives safely on disk. Network failure between the broker and consumer does absolutely nothing to the stored data.
  • Consumer's poll() call times out — The consumer was waiting for the broker's response, but the network is down. After request.timeout.ms (30 seconds), the consumer gets a TimeoutException.
  • Consumer stops sending heartbeats — Consumers must regularly send a "I'm still alive" signal (heartbeat) to Kafka's Group Coordinator. If heartbeats stop for longer than session.timeout.ms (45 seconds), the Group Coordinator declares this consumer dead.
  • Kafka triggers a rebalance — When a consumer dies, Kafka needs to redistribute its partitions to the remaining live consumers. This process is called a rebalance. It's automatic — you don't do anything manually.
  • Another consumer picks up from the last saved position — The surviving consumer starts reading from the last committed offset. This is the last offset the failed consumer had saved as "processed." Nothing is missed.
  • When network recovers, the old consumer rejoins — It reconnects to Kafka, announces itself to the Group Coordinator, and gets partition(s) assigned again after the next rebalance cycle.
  • Dangerous hidden trap — duplicate processing — If the failed consumer had already processed a message (say, charged a customer's card) but hadn't committed the offset before the crash, the new consumer picks up from before that point and processes the same message again. The card gets charged twice.
  • Fix: commit offset only AFTER you've fully processed — Use commitSync() after your business logic completes. This way, if you crash mid-processing, you re-process the same message (at-least-once), but at least you don't silently skip it.
Key insight: Kafka's pull model (consumer fetches from broker, not pushed to it) means the broker never "loses" a message because a consumer disconnected. The broker just waits. The consumer comes back and picks up exactly where it left off.
🟣 Scenario 3 — Producer Is Fast (10,000/sec), Consumer Is Slow (100/sec) SPEED MISMATCH / LAG
Analogy: A factory (producer) makes 10,000 boxes per hour, but the warehouse worker (consumer) can only unpack 100 boxes per hour. The warehouse fills up. Eventually old boxes get thrown out to make room — before the worker ever gets to them.
  • Kafka does NOT slow down or block the producer — The producer writes at full speed (10,000/sec). Kafka is designed to be a buffer between fast producers and slow consumers. That is literally its purpose. The partitions just accumulate more and more messages.
  • Consumer lag starts building immediately — At 10,000 produced and 100 consumed per second, lag grows by 9,900 messages every second. After 1 hour, the consumer is 35.6 million messages behind. After 1 day, it's 856 million messages behind.
  • Lag = your consumer is reading stale old data — When lag is high, the consumer is processing events from hours or days ago — not what's happening right now. For fraud detection, real-time dashboards, or alerting systems, this means you're reacting to old information — which is useless or dangerous.
  • If lag exceeds retention window → data loss for that consumer — Kafka's retention policy deletes old segments after (say) 7 days. If the consumer is so far behind that the messages it needs have been deleted, it gets an OffsetOutOfRangeException. Those messages are permanently gone.
  • Kafka itself is completely fine — The broker doesn't crash, the producer doesn't crash. Only the consumer is in trouble. Kafka treats this as the consumer's problem to solve.
4 Ways to Fix Consumer Lag — Simply Explained
FIX 1
Add more consumers to the group. If a topic has 6 partitions and you only have 1 consumer, that 1 consumer reads all 6 partitions alone. Add 5 more consumers → each one reads only 1 partition → 6× faster total throughput. Max useful consumers = number of partitions.
FIX 2
Increase the number of partitions. More partitions = more consumers working in parallel. If you have 10 consumers but only 3 partitions, 7 consumers sit completely idle — they have nothing to read. Increase partitions to 10 and all 10 consumers work simultaneously.
FIX 3
Make each consumer process faster. Increase max.poll.records (fetch more messages per call), write records to your DB in a batch (one INSERT for 500 rows instead of 500 INSERTs), use async processing, or use a thread pool inside the consumer.
FIX 4
Monitor lag and alert early. Don't wait until messages are deleted to notice the problem. Set up an alert when lag exceeds your threshold (e.g. "if any partition is more than 100,000 messages behind, page someone"). Use kafka-consumer-groups.sh --describe or Kafka's JMX metrics to see lag per partition in real time.
Remember: LAG = LOG-END-OFFSET − CURRENT-OFFSET. If this number is growing over time, you have a problem. If it's stable or shrinking, you're keeping up.

Partitioner

The partitioner decides which topic partition receives each message. This is critical for ordering guarantees and load distribution.

  • Default (key present) — murmur2 hash of key mod numPartitions. Same key always lands on same partition → ordering per key.
  • Round-robin (null key) — cycles across all partitions evenly, maximises parallelism.
  • Sticky Partitioner (Kafka 2.4+) — batches null-key messages to one partition, then switches. Reduces latency.
  • Custom — implement the Partitioner interface for business logic (e.g., VIP routing).
CustomPartitioner.java 
public class RegionPartitioner
    implements Partitioner {

  @Override
  public int partition(String topic,
      Object key, byte[] keyBytes,
      Object value, byte[] valueBytes,
      Cluster cluster) {

    List<PartitionInfo> parts =
        cluster.partitionsForTopic(topic);
    int n = parts.size();

    if (key != null) {
      String k = key.toString();
      if (k.startsWith("US-")) return 0;
      if (k.startsWith("EU-")) return 1;
    }
    // fallback: murmur2 hash
    return Math.abs(
      Utils.murmur2(keyBytes)) % n;
  }

  @Override public void configure(
      Map<String, ?> configs) {}
  @Override public void close() {}
}

  • buffer.memory (default 32 MB) — total buffer across all partitions. Producer blocks if full.

IDEAL 4 Partitions = 4 Consumers

SIMPLE EXPLANATION

3 Ways to Commit Offsets — In Plain Words, Point by Point

What does "committing an offset" even mean?
Think of it like a bookmark in a book. When you commit offset 48, you're telling Kafka: "I have finished reading and processing everything up to page 47. If I ever restart, don't go back further — resume from page 48." The commit is saved inside Kafka itself (in a special topic called __consumer_offsets), so it survives crashes and restarts.
AUTO enable.auto.commit=true EASIEST — BUT DANGEROUS
Analogy: Your book automatically bookmarks every 5 minutes whether you've actually read those pages or not.
  • Kafka automatically commits your offset every 5 seconds (controlled by auto.commit.interval.ms, default 5000ms). You write zero commit code — it just happens in the background.
  • You have no control over timing — Kafka commits after every poll cycle regardless of whether your business logic has actually finished processing those messages.
  • Risk 1 — Duplicate processing: Kafka polls records (fetches them) and commits the offset. Then your app crashes BEFORE it finishes processing them. When it restarts, Kafka sees the offset was already committed and skips those records → messages processed 0 times even though they needed to be processed once.
  • Risk 2 — Data loss in the other direction: If Kafka commits the offset before you finish processing, then you crash mid-process, those messages are considered "done" by Kafka. You'll never see them again → silent data loss.
  • When is it OK to use? Only when your processing is fully idempotent (safe to run twice) AND losing a few messages occasionally is acceptable. Example: updating a live dashboard where stale data doesn't matter.
Crash scenario: poll() fetches offsets 40–50 → auto-commit fires → crash at offset 44 → restart → Kafka says "you're at 50" → offsets 44–50 are silently skipped

enable.auto.commit=true
auto.commit.interval.ms=5000
SYNC commitSync() SAFE — BUT SLOWER
Analogy: After reading each chapter, you physically write the page number in your bookmark and wait for the librarian to stamp it as confirmed before reading the next chapter.
  • You call commitSync() yourself after you've finished processing a batch of records. This gives you full control — the offset is only committed when YOU say so.
  • It BLOCKS your thread — when you call commitSync(), your consumer thread pauses and waits until the broker confirms "yes, I've stored the offset." Only then does your code continue to the next poll(). This is what "sync" means.
  • It automatically retries on transient failures — if the network hiccups during the commit, commitSync() silently retries until it succeeds or gets a non-retriable error. You don't need to write retry logic.
  • Throughput cost — because it blocks, you're paying one full network round-trip per batch before moving on. For high-throughput consumers processing millions of messages, this adds up. But for most applications this is completely fine.
  • The pattern: process first, then commit — always call commitSync() AFTER your processing loop, never before. This guarantees at-least-once delivery: if you crash after processing but before committing, you'll re-process — but you'll never silently skip a message.
  • Committed value is offset+1 — when you commit after processing offset 47, Kafka stores 48 (not 47). It means "next time start from 48." This trips up many developers — the commit says where to START next, not what you last processed.
Pattern: poll() → process all records → commitSync() → repeat. If crash happens during processing: restart re-reads from last committed offset → at-least-once (may reprocess, but never silently skip).
ASYNC commitAsync() FAST — BUT NEEDS CARE
Analogy: You drop a bookmark in the mail box and immediately keep reading. The librarian processes it whenever they get to it — you don't wait. If the mailbox is full? The letter might get lost, but you've already moved on.
  • Non-blocking — your thread keeps running immediately — unlike commitSync(), calling commitAsync() fires off the commit request to the broker and returns instantly. Your consumer continues polling the next batch while the commit happens in the background.
  • Higher throughput than commitSync() — because you don't stop and wait for the broker's confirmation, you can process and commit simultaneously. For high-throughput pipelines, this matters.
  • Does NOT retry on failure — intentionally — if the commit fails (network hiccup), commitAsync() does NOT retry. This sounds bad but is actually the right design: if Kafka retried an async commit of offset 50 after you've already committed offset 60, it could roll the committed offset backwards → consumer would re-read offsets 50–60 again → duplicates.
  • Use a callback to catch failures — pass a callback lambda to commitAsync(). If the commit fails, your callback is called with the error. You should log it. The next successful commit will cover those offsets anyway (commits are cumulative), so occasional failures are tolerable.
  • Best practice: use commitAsync() normally + commitSync() on shutdown — during normal operation, use fast async commits. When your consumer is shutting down gracefully (finally block / shutdown hook), call commitSync() one last time to make absolutely sure the final offset is durably saved before the consumer dies.
Why no retry? Imagine: commitAsync(offset=50) fails → meanwhile you process up to offset=70 → commitAsync(offset=70) succeeds → now Kafka retries the failed commit of offset=50 → offsets 50–70 would be re-read → duplicates!
Recommended pattern:
Normal loop → commitAsync() (fast)
Shutdown finally block → commitSync() (safe)
Callback → log errors only

CONSUMER GROUPING

What Is Consumer Grouping & What Happens When It Fails?

Consumer groups are how Kafka scales reads across multiple instances — and how it recovers when one of them dies.

PART 1

What Is a Consumer Group?

Analogy: Imagine a topic is a conveyor belt at a factory carrying 1000 boxes per hour. One worker (consumer) can only unpack 200 boxes/hour. So you hire 5 workers (consumers) and divide the belt into 5 lanes (partitions). Each worker handles their own lane. Together they process 1000/hr. That team of workers is the consumer group.
WHAT IT IS
A consumer group is a named collection of consumer instances that work together to consume a topic. All consumers in the group share the same group.id. Example: 3 instances of your OrderProcessorService all set group.id=order-processor — they form one group.
KEY RULE
Each partition is assigned to exactly one consumer within the group at any time. No two consumers in the same group ever read the same partition simultaneously. This guarantees ordering — all messages from partition 2 are processed in order by exactly one consumer.
SCALE RULE
The maximum useful consumers in a group = number of partitions. If your topic has 6 partitions and you add 10 consumers to the group, 4 consumers sit completely idle — there are no partitions left for them. To use all 10, increase partitions to 10.
MULTI-GROUP
Multiple consumer groups can read the same topic independently. Example: group order-processor handles payments and group email-service sends confirmation emails — both read the same orders topic but each group has its own independent offset cursor. They never interfere with each other.

PART 2

How Does Kafka Keep Track of the Group? (Group Coordinator)

WHO MANAGES IT
Every consumer group is managed by a special broker process called the Group Coordinator. One specific broker is elected as the Group Coordinator for each group based on a hash of the group.id. All consumers in the group talk to their Group Coordinator for membership and offset management.
HEARTBEAT
Every consumer sends a heartbeat to the Group Coordinator every heartbeat.interval.ms (default 3 seconds) — a small "I'm alive" ping. The Group Coordinator keeps a timer per consumer. If no heartbeat arrives within session.timeout.ms (default 45 seconds), the consumer is declared dead.
GROUP LEADER
Among all consumers in the group, the first one to join is elected the Group Leader (a consumer-side role, different from broker leader). The Group Leader runs the partition assignment algorithm (decides which consumer gets which partitions) and reports the plan to the Group Coordinator. This is done entirely within the consumer JVM — the broker only distributes the plan.
REBALANCE
Any membership change — a consumer joins, dies, or is declared dead — triggers a rebalance. During rebalance, all consumers in the group stop consuming (stop the world in eager mode) and wait for new partition assignments. After the rebalance, each consumer resumes from the last committed offset for its newly assigned partitions.
Consumer Join Sequence (What happens when a new consumer starts)
1
Consumer starts, finds the Group Coordinator broker (via FindCoordinator API call)
2
Sends a JoinGroup request with its group.id and the topics it wants to subscribe to
3
Group Coordinator triggers a rebalance — all existing members are notified
4
Group Leader calculates new partition assignments and sends the plan via SyncGroup request
5
Each consumer receives its assigned partitions, seeks to the last committed offset, and begins polling
PART 3

What Happens When a Consumer Stops Responding?

💀 Type 1 — Consumer Crashes / Process Killed
STEP 1
Consumer process dies. All heartbeats stop immediately.
STEP 2
Group Coordinator waits session.timeout.ms (45s). After that — declares consumer dead.
STEP 3
Rebalance triggered. Partitions that were owned by the dead consumer are redistributed to remaining live consumers.
STEP 4
New owner starts reading from the last committed offset of those partitions. Any messages processed but not yet committed are re-read (at-least-once).
🐌 Type 2 — Consumer Is Alive But Too Slow (Liveness Failure)
CAUSE
Consumer calls poll() but takes too long between calls — maybe processing 500 records takes 10 minutes but max.poll.interval.ms is 5 minutes.
WHAT HAPPENS
Kafka considers a consumer that doesn't call poll() within max.poll.interval.ms as dead — even if heartbeats are still flowing. The consumer is forcibly removed from the group.
FIX
Reduce max.poll.records so each poll() cycle handles fewer records, or increase max.poll.interval.ms to match your actual processing time.
🛑 Type 3 — What If the Group Coordinator Broker Itself Fails?
STEP 1
The broker acting as Group Coordinator crashes. All consumers in the group immediately notice their connections drop.
STEP 2
Consumers call the FindCoordinator API again. Kafka's metadata layer elects a new Group Coordinator (a different broker) for this group automatically.
STEP 3
All consumers rejoin via the new coordinator — a full rebalance happens. Offset data is safe because it's stored in the __consumer_offsets topic which is replicated across brokers (not just on the failed one).
RESULT
No data loss. There's a brief pause (seconds to tens of seconds) while the new coordinator is elected and rebalance completes, but all consumers resume from exactly where they left off.
🌐 Type 4 — Consumer Not Receiving Response (Network Issues)
SYMPTOM
Consumer calls poll() but the broker never responds — requests time out. This happens due to network partition, broker overload, or firewall issues.
WHAT KAFKA DOES
poll() throws a TimeoutException after request.timeout.ms. Heartbeats also fail → after session.timeout.ms, the Group Coordinator declares the consumer dead → rebalance.
RECOVERY
When network recovers, the consumer reconnects, rejoins the group, and receives its partitions back (possibly different ones after rebalance). It resumes from the last committed offset.
SPLIT BRAIN RISK
If the consumer is alive but isolated (can't reach the broker), it may still try to process messages in memory while another consumer took over those partitions. Kafka handles this via the offset commit — whichever consumer commits last wins. Idempotent processing logic is essential here.
PART 4

The Rebalance Storm Problem & How to Avoid It

What is a Rebalance Storm?
A rebalance storm happens when rebalances keep triggering repeatedly in a cycle. Example: you deploy a rolling update of 10 consumer pods. Pod 1 restarts → rebalance → Pod 2 restarts → rebalance → Pod 3 ... all 10 trigger 10 consecutive rebalances over 10 minutes. During each rebalance, all consuming stops. This causes massive lag spikes and is a classic production incident.
CAUSE 1
session.timeout.ms too low — If set to 10 seconds and a GC pause or deployment restart takes 15 seconds, Kafka declares the consumer dead and triggers an unnecessary rebalance. Keep it at the default 45s or higher for stable clusters.
CAUSE 2
max.poll.interval.ms too low — If processing 500 records takes longer than this value, Kafka kicks the consumer out even though it's healthy. Fix: reduce max.poll.records or increase max.poll.interval.ms.
CAUSE 3
Eager rebalance protocol (default) — In eager mode, ALL partitions from ALL consumers are revoked before redistributing. Even consumers that didn't change lose their partitions momentarily. During this time, consuming stops entirely across the whole group.
Fix: Use Cooperative (Incremental) Rebalancing
With the cooperative rebalance protocol (available from Kafka 2.4+), only the partitions that actually need to move are revoked. Consumers that keep their partitions never stop. This eliminates the stop-the-world pause for most deployments.
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

Replication & Fault Tolerance

Kafka achieves durability and high availability by replicating each partition across multiple brokers. When a leader fails, a follower takes over seamlessly — keeping your data pipeline running without data loss.

REPLICATION FACTOR

What is Replication Factor — Explained Simply

In Plain English
Replication Factor is simply "how many copies of your data exist in the Kafka cluster."

Think of it like making photocopies of an important document. If you only have 1 copy and you spill coffee on it — the document is gone forever. If you have 3 copies stored in 3 different drawers — even if 2 drawers catch fire, you still have 1 copy safe.

In Kafka: Replication Factor = 3 means every message you write is stored on 3 different brokers (servers). If 2 brokers crash simultaneously, your data is still safe on the 3rd broker. The cluster keeps working.

How Replication Actually Works — Step by Step
STEP 1
Producer writes message to Partition 0 on Broker 1 (the leader). Only the leader accepts writes — followers never accept writes directly from producers.
STEP 2
Broker 2 and Broker 3 (the followers) continuously pull new messages from the leader. They don't wait to be pushed — they actively fetch new data.
STEP 3
Once Broker 2 and 3 have confirmed they have the message, they are part of the ISR (In-Sync Replicas). The leader then advances the High Watermark — the message is now "safe" and consumers can read it.
STEP 4
If acks=all, the leader sends the ACK back to the producer only after ALL ISR followers confirm. This is what prevents any data loss even if the leader crashes right after the ACK.
FAILOVER
If the leader crashes, Kafka's controller (KRaft or ZooKeeper) detects this within seconds and elects a new leader from the ISR. Consumers and producers automatically discover the new leader via metadata refresh. No manual intervention needed.

DELIVERY GUARANTEES

At-Most-Once, At-Least-Once, Exactly-Once

How Kafka delivers messages depends entirely on how you configure producers and consumers. Understanding the tradeoffs between these three modes is critical for building reliable systems.

SIMPLE EXPLANATION

All 3 Delivery Guarantees — Plain Words, Real Examples

When a Kafka message is produced, consumed, and processed — how many times can that message's effect happen?
Let's understand them using a Swiggy / Zomato food ordering example.
A customer places an order → OrderCreated event is published to Kafka → a consumer reads it and processes the order (assigns delivery partner, notifies restaurant, charges card).
AT-MOST-ONCE→ order might be silently dropped
AT-LEAST-ONCE→ order processed, but maybe charged twice
EXACTLY-ONCE→ charged and fulfilled exactly once, always
❌ At-Most-Once MESSAGE MAY BE LOST
Think of it like dropping a letter in the post box and walking away immediately — you don't wait for confirmation, and if the postman loses it, it's gone forever.
What it means, point by point:
  • The consumer commits the offset BEFORE processing the message. It's bookmarking the page before reading it.
  • If the consumer crashes after committing but before processing — Kafka thinks "done, offset committed" and never re-delivers that message. It is permanently lost.
  • Each message is processed at most once — 0 times (if crash) or 1 time (if no crash). Never twice.
  • Speed advantage: No retries, no duplicate checks. Very fast and low overhead.
  • Use when: Losing a message occasionally is acceptable. Example: live sports score updates, real-time dashboards, IoT sensor readings where stale/missing data doesn't matter.
Swiggy / Zomato Example — At-Most-Once
Imagine a customer places an order on Swiggy.
  1. Order Service publishes OrderCreated to Kafka.
  2. Consumer (Payment Service) receives the message.
  3. Consumer commits the Kafka offset immediately — before charging the card.
  4. Consumer crashes before it could charge the card or notify the restaurant.
When the consumer restarts, Kafka considers that message already acknowledged.
The order-processing event is never processed.
Customer sees "Order Placed" but restaurant never received it. No charge, no delivery. Order silently dropped.
# How to get at-most-once:
enable.auto.commit=true  # commits before your code even sees the record
# OR manually: commitSync() BEFORE process(record)
🔁 At-Least-Once MESSAGE MAY BE DUPLICATED
Think of it like a delivery courier who keeps ringing your doorbell until you sign for the package. You might end up with the same package twice if the courier didn't get your first signature — but the package is never lost.
What it means, point by point:
  • The consumer processes the message first, then commits the offset. It reads, does the work, then moves the bookmark.
  • If the consumer crashes after processing but before committing — Kafka doesn't know the message was processed. On restart it re-delivers the same message → processed twice.
  • Each message is processed at least once — 1 time normally, 2+ times if crash happens between process and commit. Never 0 times.
  • Default Kafka consumer behaviour. This is what you get out of the box with enable.auto.commit=false + commitSync() after processing.
  • Use when: You can't afford to lose messages, and your processing is idempotent (safe to run twice). Example: sending emails, writing to a DB with upsert, logging events.
Swiggy / Zomato Example — At-Least-Once
Imagine a customer places an order on Swiggy.
  1. Order Service publishes OrderCreated to Kafka.
  2. Consumer (Payment Service) receives the message.
  3. Consumer processes the order — charges the card ✓, notifies restaurant ✓.
  4. Consumer crashes before calling commitSync() — offset not saved yet.
When the consumer restarts, Kafka re-delivers the same message (offset was never committed).
The order is processed a second time.
Card charged twice, restaurant gets duplicate order notification. At-least-once: nothing lost, but duplicated.
Fix with idempotency check:
Before charging, check: "Did I already charge for OrderID=1234?" → if yes, skip. This turns at-least-once into safe at-least-once.

enable.auto.commit=false
# Then in your code:
consumer.poll() → process(record) → commitSync()
✅ Exactly-Once NO LOSS, NO DUPLICATES
Think of it like a bank transaction — either the full amount moves from Account A to Account B atomically, or nothing happens at all. There's no "half transferred" state.
What it means, point by point:
  • Each message is processed exactly once — not 0 times, not 2 times. Even if the producer retries, even if the consumer crashes, the final result is as if it happened exactly once.
  • It requires two things working together:
      1. Idempotent producer (enable.idempotence=true) — broker deduplicates duplicate sends using sequence numbers.
      2. Kafka Transactions (transactional.id + isolation.level=read_committed) — consume, process, and produce are wrapped in a single atomic transaction. Either all happen or none do.
  • How the transaction works: The producer wraps the entire read→process→write cycle in a transaction. It calls beginTransaction(), processes, produces the result, commits the offset, and calls commitTransaction(). If anything crashes, the whole transaction is rolled back — as if it never started.
  • Consumers see only committed data — with isolation.level=read_committed, consumers skip any messages from aborted/uncommitted transactions. They never see half-finished work.
  • Performance cost: Transactions add latency (~10ms overhead per transaction). Don't use this for every consumer — only where correctness is critical.
  • Use when: Financial transactions, inventory deductions, any operation where processing twice or skipping once has real-world consequences.
Swiggy / Zomato Example — Exactly-Once
Imagine a customer places an order on Swiggy.
  1. Order Service publishes OrderCreated to Kafka.
  2. Consumer begins a Kafka transaction — beginTransaction().
  3. Inside the transaction: charges the card, notifies the restaurant, commits the offset.
  4. Consumer crashes before commitTransaction() completes.
On restart: Kafka sees the open transaction → automatically rolls it back. The card charge is reversed, the offset resets. The message is re-delivered and processed again inside a fresh transaction.
Result: order processed exactly once.
Card charged once. Restaurant notified once. Customer happy. No duplicates. No lost orders. This is exactly-once.
Cost:
~10ms extra latency per transaction. Worth it for payments. Overkill for a live game score update.

⚠ Important: Exactly-Once Has Costs

Exactly-once semantics (EOS) adds non-trivial overhead: ~20-30% throughput reduction, additional broker coordination, and 2-phase commit for offsets. It also requires Kafka Streams or manual transaction management — regular KafkaConsumer+KafkaProducer combos need careful plumbing. Only enable EOS when duplicates are truly unacceptable (financial transactions, inventory updates). For most analytics pipelines, at-least-once with idempotent downstream processing is sufficient.

Message Ordering Guarantees
✅ Ordered Within a Partition

Messages with the same key always go to the same partition. That partition's consumer sees them in write order. Kafka guarantees offset monotonicity within a partition.

❌ No Order Across Partitions

Different keys go to different partitions consumed by different consumers in parallel. There is no global ordering guarantee across partitions — only within. Use a single partition only if strict total ordering is required.

Partition Count Considerations
More Partitions = More Parallelism

Consumer group parallelism is limited by partition count. 10 partitions → max 10 consumers working in parallel. Under-partitioning is a common bottleneck.

More Partitions = More Overhead

Each partition has a file handle, leader election cost, and replication overhead. Beyond a few thousand partitions per broker, ZooKeeper/KRaft latency spikes. Rule of thumb: start with throughput/target_mb_per_partition.

Repartitioning is Painful

Adding partitions breaks key-based routing for existing messages. Plan your partition count upfront. Many teams use 12, 24, or 48 for easy scaling (divisible by common consumer counts).

Key Selection Best Practices
🎯
Use Business Entity IDs

Keys like customerId, orderId, or deviceId ensure all events for one entity land on the same partition — enabling stateful stream processing per entity.

key = "customer-" + customerId
⚖️
Avoid Skewed Keys

If one key is 100× more frequent (e.g., a "system" key), one partition becomes a hotspot. Use compound keys or salting to spread load: key + "_" + (offset % N).

⚠ Avoid: key = "global-event"
🚫
Null Key = Round-Robin

No key means Kafka distributes messages evenly across all partitions (sticky batch per producer). Highest throughput, but no ordering guarantee. Good for log streaming, metrics.

key = null → round-robin

// The brain of the order side.
// Builds the OrderEvent, persists to DB, publishes to Kafka.

@Service
@RequiredArgsConstructor
@Slf4j
public class OrderService {

    private final OrderProducer  orderProducer;
    private final OrderRepository orderRepository;  // JPA / MongoDB repo

    // Called by OrderController on POST /api/orders
    public OrderResponse processOrder(CreateOrderRequest request) {

        String orderId      = UUID.randomUUID().toString();
        String correlationId = UUID.randomUUID().toString();

        // 1. Convert request DTOs → event items
        List<OrderItem> items = request.getItems().stream()
            .map(i -> OrderItem.builder()
                .itemId(i.getItemId())
                .itemName(i.getItemName())
                .quantity(i.getQuantity())
                .price(i.getPrice())
                .build())
            .collect(Collectors.toList());

        // 2. Calculate total
        BigDecimal total = items.stream()
            .map(OrderItem::getSubtotal)
            .reduce(BigDecimal.ZERO, BigDecimal::add);

        // 3. Build the Kafka event
        OrderEvent event = OrderEvent.builder()
            .orderId(orderId)
            .customerId(request.getCustomerId())
            .items(items)
            .totalAmount(total)
            .timestamp(Instant.now())
            .status(OrderEvent.OrderStatus.CREATED)
            .correlationId(correlationId)
            .deliveryAddress(request.getDeliveryAddress())
            .build();

        // 4. Persist order to database first (source of truth)
        orderRepository.save(event);
        log.info("Order {} saved to DB for customer {}", orderId, request.getCustomerId());

        // 5. Publish to Kafka — async, non-blocking
        orderProducer.publishOrder(event);
        log.info("Order {} published to Kafka", orderId);

        // 6. Return immediate response (payment happens asynchronously)
        return OrderResponse.builder()
            .orderId(orderId)
            .customerId(request.getCustomerId())
            .status(OrderEvent.OrderStatus.CREATED)
            .totalAmount(total)
            .items(items)
            .deliveryAddress(request.getDeliveryAddress())
            .createdAt(Instant.now())
            .message("Order placed! Payment processing in progress.")
            .estimatedDelivery("30-45 minutes")
            .build();
    }

    public OrderResponse getOrder(String orderId) {
        OrderEvent event = orderRepository.findById(orderId)
            .orElseThrow(() -> new OrderNotFoundException("Order not found: " + orderId));

        return OrderResponse.builder()
            .orderId(event.getOrderId())
            .customerId(event.getCustomerId())
            .status(event.getStatus())
            .totalAmount(event.getTotalAmount())
            .items(event.getItems())
            .createdAt(event.getTimestamp())
            .build();
    }

    public List<OrderResponse> getOrdersByCustomer(String customerId) {
        return orderRepository.findByCustomerId(customerId).stream()
            .map(e -> OrderResponse.builder()
                .orderId(e.getOrderId())
                .status(e.getStatus())
                .totalAmount(e.getTotalAmount())
                .createdAt(e.getTimestamp())
                .build())
            .collect(Collectors.toList());
    }

    public OrderResponse cancelOrder(String orderId) {
        OrderEvent event = orderRepository.findById(orderId)
            .orElseThrow(() -> new OrderNotFoundException("Order not found: " + orderId));

        if (event.getStatus() == OrderEvent.OrderStatus.FULFILLED) {
            throw new IllegalStateException("Cannot cancel a fulfilled order");
        }

        event.setStatus(OrderEvent.OrderStatus.CANCELLED);
        orderRepository.save(event);

        // Publish cancellation event to Kafka
        orderProducer.publishOrder(event);

        return OrderResponse.builder()
            .orderId(orderId)
            .status(OrderEvent.OrderStatus.CANCELLED)
            .message("Order cancelled successfully")
            .build();
    }
}
// Kafka producer — wraps KafkaTemplate.
// Responsible for building the ProducerRecord (with headers)
// and handling publish success/failure callbacks.

@Component
@RequiredArgsConstructor
@Slf4j
public class OrderProducer {

    private static final String ORDERS_TOPIC = "orders";
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public CompletableFuture<SendResult<String, OrderEvent>> publishOrder(OrderEvent event) {

        log.info("Publishing OrderEvent orderId={} customerId={}",
                event.getOrderId(), event.getCustomerId());

        // Use customerId as the message KEY.
        // All orders from the same customer go to the same partition
        // → guarantees ordering per customer.
        ProducerRecord<String, OrderEvent> record = new ProducerRecord<>(
                ORDERS_TOPIC,
                null,                       // partition=null → let partitioner decide
                System.currentTimeMillis(), // event timestamp
                event.getCustomerId(),      // KEY — drives partition assignment
                event,                      // VALUE — the OrderEvent POJO
                buildHeaders(event)         // metadata headers
        );

        return kafkaTemplate.send(record)
                .thenApply(result -> {
                    log.info("Order {} sent → partition={} offset={}",
                            event.getOrderId(),
                            result.getRecordMetadata().partition(),
                            result.getRecordMetadata().offset());
                    return result;
                })
                .exceptionally(ex -> {
                    log.error("Failed to publish order {}: {}",
                            event.getOrderId(), ex.getMessage());
                    throw new KafkaPublishException("Kafka publish failed for order: "
                            + event.getOrderId(), ex);
                });
    }

    // Headers travel with the message — useful for distributed tracing,
    // schema versioning, and routing in downstream consumers.
    private RecordHeaders buildHeaders(OrderEvent event) {
        RecordHeaders headers = new RecordHeaders();
        headers.add("correlationId", event.getCorrelationId().getBytes(StandardCharsets.UTF_8));
        headers.add("eventType",     "ORDER_CREATED".getBytes(StandardCharsets.UTF_8));
        headers.add("version",       "1.0".getBytes(StandardCharsets.UTF_8));
        headers.add("source",        "order-service".getBytes(StandardCharsets.UTF_8));
        return headers;
    }
}
// First consumer in the pipeline.
// Reads from "orders" topic → charges the customer's card
// → publishes result to "payment-events" topic.
// Uses MANUAL ack so the offset is only committed AFTER
// payment succeeds (at-least-once).

@Component
@RequiredArgsConstructor
@Slf4j
public class PaymentConsumer {

    private final PaymentService paymentService;
    private final KafkaTemplate<String, PaymentEvent> kafkaTemplate;

    @KafkaListener(
        topics          = "orders",
        groupId         = "payment-service-group",
        containerFactory = "orderKafkaListenerContainerFactory"
    )
    public void handleOrder(
            @Payload  OrderEvent event,
            @Header(KafkaHeaders.RECEIVED_TOPIC)     String topic,
            @Header(KafkaHeaders.RECEIVED_PARTITION) int    partition,
            @Header(KafkaHeaders.OFFSET)             long   offset,
            Acknowledgment acknowledgment) {

        log.info("PaymentConsumer: order={} topic={} partition={} offset={}",
                event.getOrderId(), topic, partition, offset);

        try {
            // 1. Process payment (charge card via payment gateway)
            PaymentEvent paymentResult = paymentService.processPayment(event);

            // 2. Publish payment result to next topic in the pipeline
            kafkaTemplate.send("payment-events",
                    event.getCustomerId(),  // key — keep same customer routing
                    paymentResult);

            // 3. Manually acknowledge ONLY after everything succeeds
            //    If we crash here, offset not committed → message re-delivered → at-least-once
            acknowledgment.acknowledge();

            log.info("Payment SUCCESS for order {} txId={}",
                    event.getOrderId(), paymentResult.getTransactionId());

        } catch (DuplicateOrderException ex) {
            // Idempotency guard — this order was already processed
            log.warn("Duplicate order detected: {} — skipping", event.getOrderId());
            acknowledgment.acknowledge(); // still commit — no need to retry

        } catch (PaymentException ex) {
            log.error("Payment FAILED for order {}: {}", event.getOrderId(), ex.getMessage());
            // Don't acknowledge → Spring will route to Dead Letter Topic
            // after max retries (configured in KafkaConfig error handler)
            throw ex;
        }
    }
}
// Business logic for payment processing.
// Called by PaymentConsumer. Talks to external payment gateway.
// Returns a PaymentEvent that is published to "payment-events" topic.

@Service
@RequiredArgsConstructor
@Slf4j
public class PaymentService {

    private final PaymentGatewayClient paymentGateway;
    private final ProcessedOrderRepository processedOrderRepo; // idempotency store

    public PaymentEvent processPayment(OrderEvent order) {

        // Idempotency check — was this order already processed?
        // Essential for at-least-once consumers to avoid double-charging.
        if (processedOrderRepo.existsById(order.getOrderId())) {
            log.warn("Order {} already processed — returning cached result", order.getOrderId());
            return processedOrderRepo.findById(order.getOrderId())
                .map(ProcessedOrder::toPaymentEvent)
                .orElseThrow();
        }

        log.info("Charging customer {} amount {} for order {}",
                order.getCustomerId(), order.getTotalAmount(), order.getOrderId());

        try {
            // Call external payment gateway (Stripe, Razorpay, etc.)
            String transactionId = paymentGateway.charge(
                    order.getCustomerId(),
                    order.getTotalAmount(),
                    order.getOrderId()      // idempotency key on gateway side too
            );

            PaymentEvent result = PaymentEvent.builder()
                .paymentId(UUID.randomUUID().toString())
                .orderId(order.getOrderId())
                .customerId(order.getCustomerId())
                .amount(order.getTotalAmount())
                .status(PaymentEvent.PaymentStatus.SUCCESS)
                .transactionId(transactionId)
                .processedAt(Instant.now())
                .correlationId(order.getCorrelationId())
                .build();

            // Save to idempotency store before returning
            processedOrderRepo.save(ProcessedOrder.from(result));

            return result;

        } catch (InsufficientFundsException ex) {
            log.warn("Insufficient funds for order {}", order.getOrderId());
            return PaymentEvent.builder()
                .paymentId(UUID.randomUUID().toString())
                .orderId(order.getOrderId())
                .customerId(order.getCustomerId())
                .amount(order.getTotalAmount())
                .status(PaymentEvent.PaymentStatus.FAILED)
                .failureReason("Insufficient funds")
                .processedAt(Instant.now())
                .build();

        } catch (PaymentGatewayException ex) {
            log.error("Gateway error for order {}: {}", order.getOrderId(), ex.getMessage());
            throw new PaymentException("Payment gateway error", ex);
        }
    }
}

@Data
@Builder
@NoArgsConstructor

public class PaymentEvent {

    private String paymentId;
    private String orderId;
    private String customerId;
    private BigDecimal amount;
    private PaymentStatus status;

    public boolean isSuccess() {

        Customer customer = customerRepo.findById(event.getCustomerId())
            .orElseThrow(() -> new CustomerNotFoundException(event.getCustomerId()));

        switch (event.getStatus()) {

            case SUCCESS -> {
                // Email: "Your order is confirmed!"
                emailClient.sendOrderConfirmation(
                    customer.getEmail(),
                    event.getOrderId(),
                    event.getAmount()

                    customer.getDeviceToken(),

                    "Your order #" + event.getOrderId()
                        + " is confirmed. Estimated delivery: 30-45 mins."
                );

                log.info("Success notifications dispatched for order {}",
                        event.getOrderId());
            }

            case FAILED -> {
                // Email: "Payment failed — please retry"
                emailClient.sendPaymentFailure(
                    customer.getEmail(),
                    event.getOrderId(),
                    event.getFailureReason()
                );

                // SMS: quick alert with retry link
                smsClient.sendSms(
                    customer.getPhoneNumber(),
                    "Payment failed for order #" + event.getOrderId()
                        + ". Reason: " + event.getFailureReason()
                        + ". Retry: app.swiggy.com/retry/" + event.getOrderId()

                        event.getOrderId());

            case REFUNDED -> {
                emailClient.sendRefundConfirmation(
                    customer.getEmail(),
                    event.getOrderId(),
                    event.getAmount()
                );
                log.info("Refund notification sent for order {}", event.getOrderId());

            default -> log.warn("No notification handler for status={} order={}",

Beginner Intermediate Advanced

Answer: Apache Kafka is a distributed event streaming platform designed for high-throughput, fault-tolerant, ordered storage and processing of event streams. It acts as a durable publish-subscribe message bus.

Use Kafka when:

  • You need to decouple services that produce and consume events independently
  • You require high throughput (millions of messages/second)
  • You need message replay (Kafka retains messages unlike traditional queues)
  • You have fan-out requirements — one event consumed by many services
  • You want real-time stream processing alongside event sourcing

Do NOT use Kafka when: you need RPC-style request/response, fine-grained message routing, or a simple task queue with low volume — use RabbitMQ or SQS instead.

  • Broker: A single Kafka server. A cluster has multiple brokers (typically 3+). One broker is the controller (manages partition leadership).
  • Topic: A named, ordered log of events. Topics are split into partitions for parallelism.
  • Partition: An ordered, immutable sequence of records within a topic. Each partition is stored on one broker (leader) with replicas on others.
  • Offset: A sequential integer that uniquely identifies a record's position within a partition. Consumers track their offset to know where they left off.
  • Leader/Follower: Each partition has one leader (handles all reads/writes) and N-1 followers (replicas that stay in sync).
Topic: orders (3 partitions, RF=3)
Partition 0: [offset 0, offset 1, offset 2, ...] → Broker 1 (leader)
Partition 1: [offset 0, offset 1, offset 2, ...] → Broker 2 (leader)
Partition 2: [offset 0, offset 1, offset 2, ...] → Broker 3 (leader)

ZooKeeper (legacy, Kafka < 3.3): External coordinator that stored cluster metadata — broker registration, topic configs, partition leadership, and consumer group offsets. Every broker had to maintain a ZooKeeper session, adding operational complexity.

KRaft (Kafka >= 3.3, default in Kafka 4.x): Kafka's own built-in Raft-based consensus mechanism. Metadata is stored in a special __cluster_metadata topic on a subset of brokers called the KRaft controller quorum.

ZooKeeper
External dependency, slow metadata propagation, no TLS on meta, ops burden
KRaft
Built-in, faster failover (<30 s), simpler ops, single security model, 10× more partitions supported

  1. Sequential disk I/O: Kafka appends to segment files sequentially — OS can flush with write-ahead log, 100× faster than random writes.
  2. Zero-copy transfer: sendfile() syscall copies data from page cache directly to network socket, bypassing user space entirely.
  3. Batching: Producer batches messages (batch.size, linger.ms). Consumers fetch batches. Fewer network round-trips.
  4. Compression: Entire batches compressed (Snappy, LZ4, ZSTD) — reduces network + disk I/O.
  5. Page cache: Kafka relies on the OS page cache rather than heap memory — no GC pauses on the data path.
  6. Partitioning: Horizontal scale — 10 brokers × 10 partitions = 100× parallel throughput compared to a single stream.

Consumer Group: A set of consumers that cooperatively consume a topic. Each partition is assigned to exactly one consumer in the group at a time — ensuring each message is processed once per group.

Key rules:

  • Partitions ≥ consumers → some consumers get multiple partitions
  • Partitions < consumers → idle consumers (no work to do)
  • Multiple groups subscribe independently — each group gets all messages

Rebalancing: When a consumer joins/leaves the group, the Group Coordinator triggers a rebalance — all partitions are temporarily unassigned and re-assigned using the configured partition.assignment.strategy (RangeAssignor, RoundRobinAssignor, CooperativeStickyAssignor).

Kafka guarantees ordering within a partition, not across partitions. To ensure a set of related messages are ordered:

  • Use a consistent partition key — all messages with the same key go to the same partition: producer.send(new ProducerRecord("orders", customerId, event))
  • Set max.in.flight.requests.per.connection=1 — prevents out-of-order delivery due to retry storms (or use enable.idempotence=true which allows up to 5 in-flight)
  • Single consumer per partition — each partition is consumed by exactly one consumer in a group, maintaining strict FIFO

Gotcha: If you need strict global ordering, use a single-partition topic — but this removes horizontal scale. Design your domain model so per-key ordering is sufficient.

At-most-once: Producer sends, no retry. Consumer commits offset before processing. Can lose messages. Used for metrics.

At-least-once: Producer retries on failure (retries>0). Consumer commits only after successful processing. May deliver duplicates on retry. Consumer must be idempotent.

Exactly-once: No duplicates, no data loss. Achieved via:

// Producer side
enable.idempotence=true
acks=all
transactional.id=order-producer-1

// Consumer side
isolation.level=read_committed

// Kafka Streams
processing.guarantee=exactly_once_v2

Exactly-once cost: ~20% throughput reduction due to transaction coordinator overhead. Use only when truly needed (financial transactions).

Consumer offsets are stored in the internal __consumer_offsets topic (50 partitions, compacted). Each consumer group commits the next offset to be consumed (committed offset = last processed offset + 1).

Auto commit (enable.auto.commit=true): Kafka commits the highest polled offset every auto.commit.interval.ms (default 5 s). Risk: commits before processing is complete → at-most-once on crash.

Manual commit:

// Spring Kafka — commit after processing
acknowledgment.acknowledge(); // MANUAL_IMMEDIATE
consumer.commitSync(); // raw API

Interview tip: Always use manual commits with enable.auto.commit=false for at-least-once guarantees. Commit only after the record is fully processed and any downstream writes are durable.

  1. Consumer stops sending heartbeats to the Group Coordinator.
  2. After session.timeout.ms (default 45 s), the coordinator marks the consumer as dead.
  3. A group rebalance is triggered — the crashed consumer's partitions are reassigned to remaining consumers.
  4. The new owner starts consuming from the last committed offset.
  5. Any messages polled but not yet committed are reprocessed → at-least-once delivery.

Key settings to tune:

  • session.timeout.ms — how long before consumer is declared dead (lower = faster failover)
  • heartbeat.interval.ms — must be <⅓ of session.timeout
  • max.poll.interval.ms — max time between polls; if exceeded, consumer is removed from group even if alive

ISR (In-Sync Replicas): The set of replicas that are fully caught up with the partition leader. A replica is in the ISR if it has fetched all messages within replica.lag.time.max.ms (default 30 s). If a follower falls behind, it is removed from the ISR.

min.insync.replicas: Broker-level config (default 1) that sets the minimum number of ISR replicas that must acknowledge a write for it to succeed. With acks=all + min.insync.replicas=2:

RF=3, min.insync.replicas=2
→ Write succeeds if at least 2 of 3 replicas are in ISR
→ Cluster survives 1 broker failure without data loss
→ If only 1 ISR replica remains → NotEnoughReplicasException

Golden rule: RF=3, min.insync.replicas=2, acks=all → production-safe configuration. Tolerates 1 broker failure. Never set min.insync.replicas=RF — no tolerance for failure.

Log compaction retains only the latest record for each key in a partition. Older records with the same key are eligible for removal during compaction. A null-value record (tombstone) signals deletion of a key entirely.

Use when:

  • Topic represents the latest state of an entity (user profile, product inventory)
  • CDC topics — consumers catching up only need the latest DB row state
  • Kafka as a source of truth / event store for event sourcing patterns

Do NOT use when: you need a full history of every change (use time-based retention instead).

Duplicates arise on the producer side (retries), consumer side (crash before commit), or both. Three approaches:

  1. Idempotent Producer: enable.idempotence=true — broker assigns a sequence number per producer; re-sent messages with same sequence are deduplicated automatically within a session.
  2. Idempotent Consumer: Store a processed message ID in a database. Before processing, check: SELECT 1 FROM processed_events WHERE event_id = ?. Skip if already seen.
  3. Transactions: Use Kafka's exactly-once transactions to atomically write to output topic and commit offset — zero duplicates, but ~20% throughput cost.

Key requirements to clarify: Channels (email/SMS/push), delivery guarantees, retry logic, throughput, ordering per user.

Design decisions:

  • One topic per channel OR a single topic with channel field + consumer-side filtering
  • Partition by userId — ensures per-user ordering (email before SMS for same event)
  • Retry topics with exponential backoff: notifications-retry-1 (5 s), notifications-retry-2 (30 s), notifications-retry-3 (2 min)
  • DLT with alerting — never silently drop a notification
  • Idempotency key on each notification event — deduplicate on consumer side using Redis SETNX
  • Rate limiting per user using a Kafka Streams sliding window count

Formula (rule of thumb):

partitions = max(target_throughput / broker_throughput,
                target_throughput / consumer_throughput)

Practical rules:

  • Start with 1 partition per consumer instance you expect at peak
  • A single partition/consumer pair handles ~10–100 MB/s depending on message size and processing cost
  • More partitions = more parallelism but more overhead (file handles, election time, end-to-end latency)
  • Partitions can only be increased, never decreased — over-provision slightly
  • Consider ordering requirements — if strict per-entity ordering is needed, use the entity count as a floor

Example: 100 K msg/sec at 1 KB each = 100 MB/s. Each consumer handles 10 MB/s → 10 partitions minimum. Add 20% headroom → 12 partitions.

Strangler Fig Pattern with Kafka: Extract services incrementally, using Kafka as the bridge between old and new systems.

  1. Identify bounded contexts — find cohesive modules in the monolith (Order, Payment, Inventory)
  2. Add CDC first — use Debezium to stream DB changes into Kafka without changing monolith code
  3. Build new services as consumers — new microservices consume Kafka events and build their own read models
  4. Dual-write period — monolith and new service run in parallel; compare outputs for consistency
  5. Cut over — route new traffic to the microservice, deprecate monolith code path
  6. Repeat — extract next bounded context

Key risks: Event ordering during dual-write, schema evolution compatibility, operational complexity increase. Mitigate with feature flags and thorough integration tests.
